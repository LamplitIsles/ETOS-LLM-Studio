# 日志怎么做、怎么读、怎么分析

日志的作用是重建**输入、状态决策、实际结果之间的因果关系**。只输出“函数被调用”“View 刷新”通常不足以判断谁改坏了状态；先围绕一个可观察不变量，记录最少但能区分解释的字段。

## 1. 按症状挑边界

| 症状 | 最小观察链 | 用来区分什么 |
| --- | --- | --- |
| 点击后键盘打不开/立即关闭 | 命中目标、UIKit 开始/结束编辑、模型焦点、请求/撤销 first responder 的来源 | 没命中、被禁用、焦点同步反向撤销，分别取证 |
| 图片或数据串到另一个页面 | 请求开始、所属页面/操作、缓存来源、返回、接受/丢弃决定、显示身份 | 返回晚、请求身份复用、旧 scope 仍可写当前状态 |
| 内容倒退、重复或换序 | 输入来源和关系、归约前后、派生 ID/值/序、列表提交 | 生产者就错、合并错、投影错、呈现错 |
| 滚动跳动/布局闪烁 | 上述可见快照，加行矩形/行高、content size/offset、bounds/insets、键盘/控件高度、手势与滚动请求 | 内容变化、二次测量、视口变化或显式定位 |
| 慢或卡顿 | 操作开始/结束、各边界等待、主线程工作区间、必要的 Instruments 测量 | I/O 等待、队列积压、计算、布局或动画耗时 |

先观测相邻边界，找到缺口后再向外展开。不要一次记录所有对象或让日志本身触发布局、焦点变化、额外请求或重复订阅。为日志替换 delegate、强制 layoutIfNeeded 等会改变故障条件，须有独立实验理由。

## 2. 关联字段与语义

| 字段 | 语义 |
| --- | --- |
| run / build | 此次运行及实际产物身份，避免拼接两个版本的日志 |
| t | 进程内单调时间；记录事件采样时刻，不是文件写入时刻 |
| event / source | 固定阶段名和来源，例如 input、reduce、apply、drop、layout；区分用户动作、回调、订阅、恢复 |
| scope / op | 运行内临时 token，分别关联页面/会话和一次操作，不输出真实业务 ID |
| owner / gen | 谁在作决定；已有生命周期代次/任务身份是否仍匹配，不因此新增产品协议版本 |
| before / after | 针对不变量的数值/布尔/变化关系，不是整份业务内容 |
| accepted / reason | 哪个分支实际接受或丢弃；原因用固定枚举，不直接写错误对象 |

关键做法：**在决策发生处捕获值，然后再异步写日志。** 若把“读取当前状态”也排入后续异步任务，日志可能描述的是另一个时刻；捕获真实来源比事后从结果猜来源可靠。

耗时与进程内事件排序统一使用一种单调时基，例如已有的 CACurrentMediaTime() 或 ProcessInfo.processInfo.systemUptime；墙钟用于关联用户报告的大致时间，不能拿系统校时后的时间差计算操作耗时。

身份、内容相等和排列分别比较。集合数量未变时仍应比较有序身份；内容比较使用可见语义，不把所有内部字段都叫“改变”。动态内容可按授权记录 same/prefix/shrink/replace 等关系；比较关系缺失时明确说“不知道”，不能从数量或字数推断。

### 日志出口

优先接入项目已有日志；使用 OSLog/Logger 或诊断文件均可，先用一条合成事件确认日志能被读回、级别和隐私策略符合本次采集需要，再请用户复现。不要先假设 debug 日志一定被持久保存。

需要持久文件时：一个任务前缀、明确文件名、容量/轮转上限；输出只异步写入已经采样的记录。页面退出移除监听器、停止 display link；读写失败输出不含路径和业务信息的固定错误类别。

正常 App 默认只取已约定的数值、布尔、固定类别和运行内关联 token。真实正文、资源 URL、账号、凭据、原始错误描述不进入日志；业务 ID 或正文哈希不能自动视作脱敏。原始 payload 和帧重放使用 test-owned 合成数据。扩充真实采集字段遵守用户当次授权。

## 3. 怎么从设备读回来

复用常驻 Mac、已有构建缓存和固定 build/install 入口；用户只做必要交互，agent 负责取日志。先核对安装版本和产物，采集结果与其对应。只有已经明确获准的诊断输出可被读取；既有凭据和整个沙盒不作为日志来源。

当使用 App 自有诊断文件时，现有 Xcode devicectl 支持读取指定文件。以下是命令结构，变量必须是本次已确认/获准的设备、App、相对日志路径和自有输出文件，**不是让 agent 枚举容器**：

```sh
xcrun devicectl device copy from \
  --device "$ETOS_DIAG_DEVICE" \
  --domain-type appDataContainer \
  --domain-identifier "$ETOS_DIAG_BUNDLE" \
  --source "$ETOS_DIAG_RELATIVE_LOG" \
  --destination "$ETOS_DIAG_OUTPUT" \
  --quiet --timeout 30
```

设备信息若需临时 JSON，用本轮临时目录解析，不把原始设备信息转存到报告。取回后检查容量、编码、预期日志前缀；只清理本轮自有临时文件。统一日志已有获准的读取通道时直接复用，不必为了统一格式另建文件。

日志拿不到时，分别核对“采样未触发、级别未保留、未flush、产物不符、设备不可达、路径/权限不符”，输出准确的失败阶段。不要把“没有日志”写成“该事件没有发生”；也不要为掩盖读取失败过滤掉全部可用于诊断的错误类别。

## 4. 怎么读：先重建一次操作

1. 固定 run/build，选用户确认异常的操作或时间窗，加上它之前的最后正常状态。将不同 run 分开。
2. 用 scope/op token 关联同一动作的入口、异步结果、状态决定和最终效果。跨主机单调时钟不可直接排序；用同一捕获流、消息/请求对应和实际发送/接收边界建立关系。
3. 按**采样时刻**重建事件表：时间、来源、输入关系、接受/丢弃、状态结果、实际呈现。文件输出先后和 Task 创建先后不等于执行/接受先后。
4. 找出最后符合不变量的记录、第一条违反它的记录，再向前定位写入者。只缺其中一层时补这一层，不重新铺满日志。

从本轮脱敏日志中筛阶段可以用：

```sh
rg -n 'event=(input|reduce|apply|drop|layout|focus|scroll)' "$ETOS_DIAG_OUTPUT"
```

具体字段/时间窗按实际格式调整；筛选是为了形成事件表，不是只数 warning、reload 或 objectWillChange 的次数。保留原始脱敏文件和筛选规则，避免过滤掉会推翻候选的记录。

## 5. 怎么分析：日志给候选，干预给因果

以下是**合成示意，不是本次已经执行的设备日志**。

### 焦点被来回撤销

```text
t=1.00 event=input source=tap target=editor
t=1.01 event=focus source=UIKit editing=1 modelFocus=0
t=1.02 event=apply source=bridge action=resign reason=modelFocusFalse
t=1.03 event=focus source=UIKit editing=0
```

日志将“没点中”与“点中了、随后被同步撤销”区分开。下一步检查焦点拥有者和回写路径；受控改变该同步条件，预测 resign/结束编辑是否消失。单有 tap 或 editing=0 不够作这个结论。

### 旧操作的结果写入新页面

```text
t=2.00 event=input scope=S1 op=O1 action=load
t=2.10 event=input scope=S2 action=enter
t=2.30 event=apply scope=S2 sourceOp=O1 sourceScope=S1 accepted=1
```

首先核实记录的是写入时实际 scope，而不是异步 logger 后读的 scope。若正确，再用 held callback 让 S1 结果在进入 S2 后到达，对照留在 S1 的场景。主线程串行没有证明结果有效；加入任意延时也没有解释该所有权错误。

### 数据稳定，几何却反向变化

```text
t=3.00 event=apply identitiesSame=1 visibleValuesSame=1 orderSame=1
t=3.10 event=layout row=R1 y=200 height=80 offset=0 viewport=600
t=3.14 event=layout row=R1 y=-100 height=80 offset=0 viewport=600
t=3.18 event=layout row=R1 y=50 height=80 offset=0 viewport=600
```

先核对其间键盘、手势、显式滚动、邻行尺寸以及模型/呈现坐标。offset 固定并不排除行移动；没有完整可见快照等价证据时，也不能先宣布“纯布局问题”。区分框架正常的一次位置过渡与用户报告的异常反复，必要时再用 Instruments 或视图调试器补度量。

## 6. 报告和下一步

每个候选写“证据支持/反对、若成立会出现什么、下一步只改变哪个变量”。用真实实现和 fake/受控传输验证；明确 fixture 是否只是附近缺陷，是否匹配原场景。一次试验的多行异常不当作多次复现；报告实际 x/y 和不可控前提。

最终报告至少能回答：哪个版本、什么输入、哪个边界首次错、日志怎样支持、对照是否推翻其他解释、修复后原始体验怎样、还缺什么。过期回调、先发新值后发旧值、派生身份不稳定等只是可验证的类别，不是遇到同类症状就套用的答案。
